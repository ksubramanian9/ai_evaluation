# Research supplement: sandboxing-untrusted-code

As of 2026-11-21. Web access worked (WebFetch, curl, pdftotext on downloaded PDFs).

## Claims

- **Codex sandbox (Chen et al. 2021, sec. 2.3).** Generated programs "are often incorrect" and public code has unknown intent, so executing them is a security risk. Goals: prevent programs from "modifying, gaining persistence on, accessing sensitive resources on, or exfiltrating data from a host or network". gVisor was "the main host protection component" because runtimes like Docker "can share host resources with containers"; network-adjacent hosts are protected by "eBPF-based firewall rules that prevent inbound and outbound connections except for those required for experiment control". https://arxiv.org/abs/2107.03374 (read: section 2.3 full text from the PDF).
- **human-eval execution guard.** `reliability_guard` docstring: "This function is NOT a security sandbox. Untrusted code, including, model-generated code, should not be blindly executed outside of one." It nulls destructive functions (os.kill, os.fork, os.system, subprocess.Popen, os.remove, shutil.rmtree and others) and sets RLIMIT_AS/RLIMIT_DATA/RLIMIT_STACK only when a memory limit is passed; `unsafe_execute` calls it without one. Timeouts: SIGALRM-based `time_limit` plus killing the worker process after `timeout + 1`. Code runs in a temporary directory with I/O swallowed. The WARNING comment says users "are strongly encouraged to sandbox this evaluation suite". In the current master the `exec` line under "uncomment the following line" is active, not commented. https://github.com/openai/human-eval/blob/master/human_eval/execution.py (read: full file via raw.githubusercontent.com and WebFetch summary).
- **Docker isolation.** Namespaces are "the first and most straightforward form of isolation"; cgroups do resource accounting and "are essential to fend off some denial-of-service attacks" but do not stop data access; capabilities use an allowlist; default capabilities and mounts "may provide incomplete isolation ... when used in combination with kernel vulnerabilities"; only trusted users should control the daemon. https://docs.docker.com/engine/security/ (read: full page via summary).
- **Docker resource defaults.** "A container has no resource constraints" by default; `--memory`, `--memory-swap` (equal to `--memory` means no swap), `--cpus`; on OOM the kernel kills processes in the container. https://docs.docker.com/engine/containers/resource_constraints/ (read: full page via summary).
- **Docker run flags.** `--read-only` mounts the root filesystem read-only; `--pids-limit` caps processes; `--tmpfs` makes an in-memory mount; `--cap-drop`; `--security-opt no-new-privileges`; `--rm` removes the container and anonymous volumes on exit; `--runtime` selects the runtime. https://docs.docker.com/reference/cli/docker/container/run/ (read: flag table via summary).
- **Docker `none` network.** Fully isolates the network stack; "only the loopback device is created". https://docs.docker.com/engine/network/drivers/none/ (read: full page).
- **gVisor security model.** Aims to "provide additional defense against the exploitation of kernel bugs by untrusted userspace code"; the Sentry implements syscalls so none pass through to the host. Does not protect against hardware side channels; resource exhaustion relies on host cgroups; "Network policy controls should be applied at the container level"; "A sandbox is not a substitute for a secure architecture." https://gvisor.dev/docs/architecture_guide/security/ (read: full page via summary).
- **Firecracker design.** Guest is untrusted ("all vCPU threads are considered to be running malicious code as soon as they have been started"); KVM is "the first layer of isolation"; minimal device model; seccomp filters; jailer (cgroups, chroot, drop privileges), production use "only via the jailer"; guest egress "should be filtered at the host-level"; rate limiters on block/net devices. Side channels not covered on this page. https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md (read: full page via summary).
- **SWE-bench harness.** Evaluation "performed in a containerized Docker environment"; three image layers (base, ~60 environment images, instance images); cache levels none/base/env/instance (instance ~2,000GB); `--clean True`; 120GB disk, 16GB RAM, workers below min(0.75 * cpu_count, 24). Network isolation is not described. Can run on Modal. https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/docker_setup.md and https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/evaluation.md (read: full pages via summary).
- **Inspect AI sandboxes.** Built-in `docker` and `local` ("no sandbox"); external k8s and others; each sample gets its own sandbox instance and cleanup is automatic; generated Compose config uses `network_mode: none` but a custom Compose file must set it itself; CPU/memory via Compose `cpus`/`mem_limit`; `exec()` takes a timeout; warns "Don't count on a non-root container user to contain an adversarial model". https://inspect.aisi.org.uk/sandboxing.html (read: full page via summary).
- **Anthropic on trial isolation.** "Each trial should be 'isolated' by starting from a clean environment"; shared state "(leftover files, cached data, resource exhaustion) can cause correlated failures" and "can also artificially inflate performance"; example of Claude examining git history from previous trials. https://www.anthropic.com/research/demystifying-evals-for-ai-agents (read: relevant section via summary).
