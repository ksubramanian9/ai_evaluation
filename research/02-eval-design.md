## task-definition-and-success-criteria
**Why it matters.** Anthropic's docs say to define success criteria before building evals; good criteria are specific, measurable, achievable, relevant, and most use cases need multidimensional criteria (example: F1 >= 0.85, 99.5% non-toxic, 95% of responses < 200ms) [CLAUDE-EVAL]. OpenAI's workflow starts with "Define eval objective" [OAI-BP]. Measurement-theory framing: unobservable constructs must be inferred via a measurement model whose assumptions can diverge from the intended concept [Jacobs & Wallach](https://arxiv.org/abs/1912.05511). Evaluation should be grounded in real human needs/context (socio-technical gap) [Liao & Xiao](https://arxiv.org/abs/2306.03100).
**Failure modes.** "Good performance" without an operational definition [CLAUDE-EVAL]; criteria that exist only after seeing outputs ("criteria drift": users need criteria to grade, but grading helps define criteria) [Shankar et al.](https://arxiv.org/abs/2404.12272); target unrealistic for current model capability [CLAUDE-EVAL]; mismatch between construct and operationalization [Jacobs & Wallach](https://arxiv.org/abs/1912.05511).
**Practice.** Pick an app (e.g., support-ticket summarizer). Write 4-6 criteria, each rewritten to pass the specific/measurable/achievable/relevant test; attach a measurement method and threshold to each. Grade 20 outputs, then revise criteria and log what changed (observe criteria drift yourself).
**Mastery check.** (1) Rewrite "the bot should be helpful" as 3 testable criteria with measurement methods. (2) Explain criteria drift and how an iterative process handles it. (3) Which criteria are construct-level vs directly observable, and what assumption links them?
**Sources.** [CLAUDE-EVAL]; [OAI-BP]; https://arxiv.org/abs/1912.05511; https://arxiv.org/abs/2306.03100; https://arxiv.org/abs/2404.12272. Practitioner: none added.

## quality-dimensions-taxonomy
**Why it matters.** HELM maps use cases (scenarios) and desiderata (metrics) and measures seven metric categories: accuracy, calibration, robustness, fairness, bias, toxicity, efficiency; 30 models x 42 scenarios, coverage of core scenarios raised from 17.9% to 96.0% [HELM]. Anthropic lists example dimensions: task fidelity, consistency, relevance/coherence, tone/style, privacy, context utilization, latency, price [CLAUDE-EVAL]. RAG-specific separation: faithfulness, answer relevance, context relevance [RAGAs](https://arxiv.org/abs/2309.15217). Healthcare example of behavioral dimensions: accuracy, instruction following, communication [HealthBench](https://arxiv.org/abs/2505.08775).
**Failure modes.** Single aggregate score hiding trade-offs (HELM's motivation: broad multi-metric measurement, not accuracy alone) [HELM]; conflating retrieval quality with generation faithfulness in RAG [RAGAs](https://arxiv.org/abs/2309.15217); applying an irrelevant dimension (citation accuracy matters in medical, less in casual chat) [CLAUDE-EVAL].
**Practice.** For one app, build a dimension x scenario matrix (rows: dimensions from HELM/Anthropic lists; columns: 3-5 scenarios). Mark each cell: measured / not measured / not relevant, with justification. Compute your own "coverage %" like HELM.
**Mastery check.** (1) Name two dimensions that trade off and show a pair of outputs illustrating it. (2) For RAG, which dimension fails if retrieval is poor but the answer is fluent? (3) Which dimensions need no model/human judge?
**Sources.** [HELM]; [CLAUDE-EVAL]; https://arxiv.org/abs/2309.15217; https://arxiv.org/abs/2505.08775. NIST AI RMF 1.0 released 2023-01-26, GenAI Profile NIST-AI-600-1 released 2024-07-26 per https://www.nist.gov/itl/ai-risk-management-framework (the page does not list trustworthiness characteristics; the list itself is UNVERIFIED here; page notes RMF is being revised, as-of 2026-11-20).

## metric-selection
**Why it matters.** Metric choice can manufacture conclusions: apparent "emergent abilities" can arise from nonlinear/discontinuous metrics and vanish with continuous ones [Schaeffer et al.](https://arxiv.org/abs/2304.15004). Anthropic maps task to grader: exact match (classification), embedding cosine similarity (consistency), ROUGE-L (summarization), LLM Likert/binary graders (tone, PHI detection); recommends a different model as grader than generator [CLAUDE-EVAL]. OpenAI warns against relying only on generic academic metrics and notes judge position/verbosity bias [OAI-BP]. Judge agreement: GPT-4 >80% with humans on MT-bench, with position, verbosity, self-enhancement bias [Zheng et al.](https://arxiv.org/abs/2306.05685). For agents: pass@k vs pass^k (75% per-trial -> ~42% pass^3) [ANTH-AGENT].
**Failure modes.** Metric/construct mismatch (ROUGE for faithfulness; UNVERIFIED as cited claim); discontinuous metrics hiding progress [Schaeffer](https://arxiv.org/abs/2304.15004); judge biases [Zheng](https://arxiv.org/abs/2306.05685); using pass@k when consistency matters [ANTH-AGENT]; imbalanced classes with accuracy (see baselines node).
**Practice.** Take 100 summaries (any public summarization set). Score with ROUGE-L, embedding cosine, and an LLM judge using a 3-point rubric; hand-label 30; compute rank correlation of each metric with your labels. Report which metric you would use for which decision.
**Mastery check.** (1) Pick metrics for 3 tasks (extraction, RAG answer, agent task) and justify. (2) Show how swapping exact-match for per-token accuracy changes a scaling curve. (3) Compute pass@3 vs pass^3 for p=0.8.
**Sources.** [CLAUDE-EVAL]; [OAI-BP]; https://arxiv.org/abs/2304.15004; https://arxiv.org/abs/2306.05685; [ANTH-AGENT]; [HELM]. Prereq `ml-metrics` is in another branch (not checked).

## golden-datasets
**Why it matters.** Start small: "20-50 simple tasks drawn from real failures"; good task = two domain experts reach the same verdict; use reference solutions; balance should/shouldn't-happen cases [ANTH-AGENT]. Datasets should come from production data, expert references, synthetic data, historical logs, covering typical/edge/adversarial cases [OAI-BP]. Anthropic: mirror real task distribution, include edge cases (irrelevant/overly long input, ambiguity) [CLAUDE-EVAL]. Benchmarks need reliability, annotation quality, headroom [Bowman & Dahl](https://arxiv.org/abs/2104.02145) (abstract cites dataset design, annotation reliability, size, social bias as needed repairs).
**Failure modes.** Datasets that don't reproduce production traffic [OAI-BP]; one-sided sets that reward overdoing a behavior [ANTH-AGENT]; broken tasks (near-zero scores likely mean broken task/grader) [ANTH-AGENT]; saturation (eval stops discriminating once all solvable tasks pass; graduate to regression suite) [ANTH-AGENT]; unreliable/biased labels [Bowman & Dahl](https://arxiv.org/abs/2104.02145). Adversarial human-in-loop collection (Dynabench) is one remedy for saturation/fragility [Kiela et al.](https://arxiv.org/abs/2104.14337).
**Practice.** Mine 30 real/realistic failures for an app (or use a public QA set), write input + expected behavior + grader, include 10 negative cases, have a second person (or you a day later) independently label; report agreement and fix ambiguous items. Version the file with a changelog.
**Mastery check.** (1) What makes a task "two experts agree"? (2) How would you detect a broken item? (3) When does a golden set become a regression suite and what replaces it?
**Sources.** [ANTH-AGENT]; [OAI-BP]; [CLAUDE-EVAL]; https://arxiv.org/abs/2104.02145; https://arxiv.org/abs/2104.14337.

## coverage-and-slicing
**Why it matters.** Aggregate accuracy overestimates performance; CheckList uses a capability x test-type matrix, found critical failures in commercial models, and users wrote ~2x tests and found ~3x bugs [CheckList](https://arxiv.org/abs/2005.04118). Model cards report disaggregated results across demographic/cultural/phenotypic and intersectional groups [Mitchell et al.](https://arxiv.org/abs/1810.03993). HELM quantifies coverage (17.9% -> 96.0%) [HELM]. Slice discovery finds underperforming coherent subsets automatically; Domino recovers 36% of 1,235 benchmark slices [Eyuboglu et al.](https://arxiv.org/abs/2203.14960).
**Failure modes.** Aggregate hides subgroup failure [Mitchell](https://arxiv.org/abs/1810.03993); slices too small for stable estimates (UNVERIFIED in sources fetched; connect to Miller's error-bar paper https://arxiv.org/abs/2411.00640); unlabeled slices in high-dim inputs [Eyuboglu](https://arxiv.org/abs/2203.14960); coverage by count not by input-space diversity (UNVERIFIED).
**Practice.** Tag your golden set with 3-4 metadata attributes (topic, length, language, difficulty). Report accuracy per slice with bootstrap CIs; identify the worst slice; add targeted cases and a CheckList-style invariance test (e.g., typo/name swap).
**Mastery check.** (1) Overall 90% yet one slice at 60%: how large must the slice be to be sure? (2) Draw a capability x test-type matrix for your app. (3) Why report intervals per slice?
**Sources.** https://arxiv.org/abs/2005.04118; https://arxiv.org/abs/1810.03993; https://arxiv.org/abs/2203.14960; [HELM]. (Group-DRO and ML Test Score slice tests not verified.)

## synthetic-data-generation
**Why it matters.** Model-written evals can be cheap and good: 154 datasets, crowdworkers agreed with 90-100% of labels, and they surfaced inverse scaling and sycophancy [Perez et al.](https://arxiv.org/abs/2212.09251). Self-Instruct pipeline: generate, filter invalid/near-duplicate, finetune [Wang et al.](https://arxiv.org/abs/2212.10560). RAG test-set generation as a RAG-eval use [RAGAs](https://arxiv.org/abs/2309.15217) (testset generator itself UNVERIFIED). OpenAI lists synthetic examples among dataset sources [OAI-BP].
**Failure modes.** Need to check factuality, fidelity, bias [Liu et al. 2024](https://arxiv.org/abs/2404.07503); loss of distribution tails when training on model output (model collapse) [Shumailov et al.](https://arxiv.org/abs/2305.17493) (relevance to eval sets is my inference); near-duplicates (why Self-Instruct filters) [Wang](https://arxiv.org/abs/2212.10560); not matching production traffic [OAI-BP]; generator = judge self-preference (judge self-enhancement bias [Zheng](https://arxiv.org/abs/2306.05685)).
**Practice.** Generate 100 test cases with an LLM from 10 seed real cases; dedupe (embedding similarity threshold), human-review 30 for validity, compare slice distribution vs real traffic; report validity rate and diversity.
**Mastery check.** (1) What fraction of synthetic items were invalid and why? (2) How do you show synthetic cases are realistic? (3) Risks if the same model generates and answers?
**Sources.** https://arxiv.org/abs/2212.09251; https://arxiv.org/abs/2212.10560; https://arxiv.org/abs/2404.07503; https://arxiv.org/abs/2305.17493; [OAI-BP].

## rubric-design
**Why it matters.** Rubrics make graders (human or LLM) consistent: Prometheus conditions on a user-supplied rubric and reference, 0.897 Pearson with humans on 45 custom rubrics (GPT-4 0.882) [Kim et al.](https://arxiv.org/abs/2310.08491); HealthBench uses conversation-specific rubrics, 48,562 criteria written by 262 physicians over 5,000 conversations [Arora et al.](https://arxiv.org/abs/2505.08775). Anthropic's LLM-graded examples use Likert 1-5 or binary classification [CLAUDE-EVAL]; OpenAI suggests pairwise or pass/fail for reliability [OAI-BP].
**Failure modes.** Rubrics drift as graders see outputs [Shankar](https://arxiv.org/abs/2404.12272); position/verbosity bias in judge application [OAI-BP]; vague anchors (UNVERIFIED in primary source); judge not validated against humans [OAI-BP].
**Practice.** Write a 1-5 rubric with anchor examples and a binary variant for one dimension; have 2 raters (or you + LLM judge) label 40 outputs; compare Cohen's kappa for both versions; refine ambiguous levels.
**Mastery check.** (1) Why might binary beat 1-5? (2) Rewrite a vague level descriptor with observable evidence. (3) How do you validate an LLM judge on a rubric?
**Sources.** https://arxiv.org/abs/2310.08491; https://arxiv.org/abs/2505.08775; [CLAUDE-EVAL]; [OAI-BP]; https://arxiv.org/abs/2404.12272.

## annotation-guidelines
**Why it matters.** Agreement coefficients (kappa-like) quantify label reliability: Artstein & Poesio survey inter-coder agreement for computational linguistics, Computational Linguistics 34(4), 2008 [ACL Anthology](https://aclanthology.org/J08-4004/) (paper content not read; PDF not extractable). Cohen's kappa = (p_o - p_e)/(1 - p_e), range -1 to 1, weights option for ordinal [scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html). Disagreement signals ambiguous tasks: "two domain experts reach same verdict" [ANTH-AGENT]; human labels calibrate automated graders [OAI-BP]; people refine criteria while labeling [Shankar](https://arxiv.org/abs/2404.12272).
**Failure modes.** Interpreting kappa with fixed bands (Landis & Koch bands are convention; primary source UNVERIFIED); kappa undefined in degenerate cases [scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html); prevalence/bias effects on kappa and alpha vs kappa (UNVERIFIED); annotator drift (UNVERIFIED).
**Practice.** Draft a one-page guideline (definitions, decision rules, 3 positive + 3 boundary examples). Two annotators label 50 items; compute kappa (sklearn), adjudicate disagreements, revise guideline, relabel 50 fresh items, show kappa improvement.
**Mastery check.** (1) Why high raw agreement but low kappa on imbalanced labels? (2) What goes in a guideline's boundary examples? (3) When do you use weighted kappa?
**Sources.** https://aclanthology.org/J08-4004/; scikit-learn page above; [ANTH-AGENT]; [OAI-BP]; https://arxiv.org/abs/2404.12272.

## contamination-and-leakage
**Why it matters.** Contaminated models look better than they are, leading to wrong conclusions; extent hard to measure [Sainz et al.](https://arxiv.org/abs/2310.18018). Black-box detection: if a benchmark was not seen, example order should not matter; significant likelihood gap for canonical order flags contamination, works down to 1.4B models/1,000 examples [Oren et al.](https://arxiv.org/abs/2310.17623). Fresh-set check: GSM1k showed up to 8% lower accuracy than GSM8k for some models, r^2=0.36 with likelihood of generating GSM8k, though frontier models showed minimal overfitting [Zhang et al.](https://arxiv.org/abs/2405.00332). Survey of definitions/mitigation [Xu et al.](https://arxiv.org/abs/2406.04244).
**Failure modes.** Public test sets in web-scale training data [Sainz](https://arxiv.org/abs/2310.18018); closed-model data not inspectable (hence black-box tests) [Oren](https://arxiv.org/abs/2310.17623); leaking test examples into your own few-shot/judge prompts or tuning (UNVERIFIED, inference); conflating overfitting with contamination [Zhang](https://arxiv.org/abs/2405.00332).
**Practice.** Take a public benchmark subset; write a held-out paraphrase/perturbed twin (50 items); compare model accuracy original vs twin; for an open-weights model also run a canonical-order vs shuffled likelihood test per Oren et al.
**Mastery check.** (1) Why does shuffle-likelihood detect contamination? (2) What do you do for a private golden set to prevent leakage into prompts/tuning? (3) What does a performance gap on a fresh twin prove and not prove?
**Sources.** https://arxiv.org/abs/2310.18018; https://arxiv.org/abs/2310.17623; https://arxiv.org/abs/2405.00332; https://arxiv.org/abs/2406.04244. Prereq `data-splits-and-leakage` is in another branch (not checked).

## validity-and-reliability
**Why it matters.** 445 LLM benchmarks reviewed by 29 experts show recurring patterns weakening construct validity; eight recommendations [Bean et al., NeurIPS 2025 D&B](https://arxiv.org/abs/2511.04703). Benchmarks should be reliable, unbiased, with headroom [Bowman & Dahl](https://arxiv.org/abs/2104.02145). General benchmarks framed as measures of "general" progress have construct validity problems [Raji et al.](https://arxiv.org/abs/2111.15366). Measurement-modeling vocabulary: construct validity/reliability [Jacobs & Wallach](https://arxiv.org/abs/1912.05511). Stability: "evaluations are experiments"; formulas for analysis, model comparison, power planning [Miller](https://arxiv.org/abs/2411.00640) (abstract only).
**Failure modes.** Construct mismatch [Bean](https://arxiv.org/abs/2511.04703); sampling noise treated as signal [Miller](https://arxiv.org/abs/2411.00640); judge bias [Zheng](https://arxiv.org/abs/2306.05685); metric artifacts [Schaeffer](https://arxiv.org/abs/2304.15004); contamination [Sainz](https://arxiv.org/abs/2310.18018).
**Practice.** Run your eval 5x at temperature>0 and with 3 prompt paraphrases; compute SE/bootstrap CI and paired difference between two prompt versions; state minimum detectable effect for your n. Separately, list the construct and 3 threats to validity.
**Mastery check.** (1) Distinguish construct validity from reliability with an example from your eval. (2) Is a 2-point gain on 200 items real? (3) Apply one Bean et al. recommendation to a benchmark you use (read the paper).
**Sources.** https://arxiv.org/abs/2511.04703; https://arxiv.org/abs/2104.02145; https://arxiv.org/abs/2111.15366; https://arxiv.org/abs/1912.05511; https://arxiv.org/abs/2411.00640.

## baselines-and-thresholds
**Why it matters.** Trivial baselines show whether a model learns anything: scikit-learn DummyClassifier (most_frequent, prior, stratified, uniform, constant) is "a simple baseline to compare against" [scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyClassifier.html). Thresholds should be achievable, based on industry benchmarks, prior experiments, research, or expert knowledge; example: <0.1% toxic of 10,000 trials [CLAUDE-EVAL]. Human agreement bounds achievable score (my inference from [ANTH-AGENT]). Headroom matters [Bowman & Dahl](https://arxiv.org/abs/2104.02145). ML Test Score gives 28 production-readiness tests [Breck et al.](https://research.google/pubs/the-ml-test-score-a-rubric-for-ml-production-readiness-and-technical-debt-reduction/) (baseline-test details UNVERIFIED).
**Failure modes.** Accuracy near majority-class rate looks good (follows from DummyClassifier docs; no direct source); unrealistic targets [CLAUDE-EVAL]; thresholds without uncertainty (see [Miller](https://arxiv.org/abs/2411.00640)); ceilings capped by annotator disagreement.
**Practice.** For a classification golden set: compute majority, stratified, and keyword-rule baselines, and human-vs-human agreement; then compare LLM prompt v1 with CIs; set a threshold justified by baseline + business cost and write it in a gate script (exit non-zero below it).
**Mastery check.** (1) Choose a threshold for a safety metric and justify with CI and n. (2) What baselines for a RAG QA system? (3) Why is human agreement a ceiling?
**Sources.** scikit-learn page above; [CLAUDE-EVAL]; https://arxiv.org/abs/2104.02145; Breck et al. link above.

## eval-driven-development
**Why it matters.** OpenAI: "Adopt eval-driven development: Evaluate early and often" because outputs vary; anti-patterns include vibe-based evals [OAI-BP]. Anthropic: write evals for planned capabilities before agents can do them, iterate to the bar; promote saturated capability evals to regression suites; read transcripts [ANTH-AGENT]. Anthropic recommends success criteria first, volume over per-item quality with automated grading [CLAUDE-EVAL].
**Failure modes.** Evals added after shipping [OAI-BP]; overfitting to the dev eval (UNVERIFIED in sources; relates to contamination/Goodhart); grader bugs mistaken for model failures [ANTH-AGENT]; criteria change mid-loop [Shankar](https://arxiv.org/abs/2404.12272); no holdout.
**Practice.** Start with 20 failing cases for a prompt task before editing the prompt; iterate prompt versions, logging pass rate with CI; keep a hidden holdout of 20 and check dev vs holdout divergence at the end.
**Mastery check.** (1) Show the red-green loop for a prompt change. (2) How do you tell prompt overfitting from real improvement? (3) When to promote a case to regression?
**Sources.** [OAI-BP]; [ANTH-AGENT]; [CLAUDE-EVAL]; https://arxiv.org/abs/2404.12272. Practitioner not collected.
